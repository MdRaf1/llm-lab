  "content": "# Research plan and skeptical prior‑art / gap analysis (through Sep 2026)\n\nSummary objective — produce a single, actionable research question and an executable gap inventory that identifies technically plausible, underexplored methods to enable substantially larger local LLM inference across memory tiers (4 GB RAM laptops → ~100 GB VRAM GPUs), with rigorous separation of exact (lossless / bit‑identical) versus lossy approaches and, for each promising gap, the 10 required deliverables.\n\n## Research question (executable)\nWhich methods (runtime-only or training/format changes) can be combined or extended to enable substantially larger local LLM inference across SSD/NVMe, DRAM, VRAM, CXL and remote memory, and heterogeneous devices, while (A) preserving bit‑identical outputs for greedy decoding from a fixed quantized checkpoint where possible, and (B) otherwise providing quantifiable, tunable lossy approximations — and which of these methods are genuinely underexplored given 2023–2026 primary sources?\n\n---\n\n## Promising gaps / candidate methods (exact vs lossy), each with the 10 required deliverables\n\nNotes on citation use: each source below is cited once in the report body and is listed in References. If an item cannot be evaluated from available evidence, that is stated.\n\n### 1) Lossless in‑compute weight compression with fused decompression (exact)\n1. Closest prior art: DFloat11 demonstrates lossless BF16 compression with GPU‑side decompression and direct inference preserving bit‑exact outputs [1]; Cloudflare Unweight provides lossless exponent/mantissa palette techniques and fused GPU kernels/autotuning for bit‑exact reconstruction [2]; ZipNN and related work show entropy coding on exponent/mantissa achieves strong lossless ratios [3].  \n2. Exact novelty claim: building on these, the gap is an end‑to‑end, generalized library that (a) compresses any quantized checkpoint format losslessly to near information‑theoretic limits and (b) exposes a minimal runtime API that transparently decodes in shared on‑chip SRAM per‑tile to feed existing tensor kernels without changing model semantics. Evidence shows parts exist but a general, widely‑portable runtime library for consumer hardware is underexplored [1][2][3].  \n3. Exactness conditions: by construction these techniques can preserve bit‑identical outputs if decompression is lossless and decoding is deterministic; both DFloat11 and Unweight report bit‑exact preservation for targeted formats [1][2].  \n4. Required changes: runtime‑only deployment is feasible for supported formats and GPUs that can host the decompression kernel (DFloat11 reports GPU kernels); broader support requires model‑format toolchain additions to emit compressed images (training change optional). Evidence does not specify a universal format converter for all families [1][2][3].  \n5. Hardware/OS/driver assumptions: fast on‑chip/shared memory capacity, GPU compute capability for custom kernels, and standard CUDA toolchains for GPU kernels (Unweight requires recent NVIDIA Hopper capabilities per their repo). Evidence does not fully specify minimal non‑NVIDIA hardware paths [2].  \n6. Bandwidth/latency upper bound: lossless compression reduces model bytes; the upper bound speedup is proportional to compression ratio under the storage→compute transfer bottleneck. Evidence shows ~30% size reduction examples (DFloat11, Unweight) yielding similar VRAM savings; arithmetic with those ratios is supported by the sources but a precise bound depends on per‑device IO not fully specified in sources [1][2].  \n7. One‑week falsifying experiment: take a quantized Llama‑3.1‑8B checkpoint used in cited results, run baseline bit‑identical inference, then run DFloat11/Unweight decompression+inference using their kernels and compare greedy outputs bit‑for‑bit and measure peak VRAM — repositories and examples cited provide kernels and instructions [1][2]. Compute/time: single modern GPU as required by the kernels; sources provide runtime measurements for these systems [1][2].  \n8. Likelihood of true novelty: medium‑high — prior work demonstrates components but a portable, consumer‑grade runtime stack remains underexplored in evidence [1][2][3].  \n9. Practical tradeoffs: latency overhead from decompression kernels, implementation complexity (kernel autotuning), and limited hardware portability; energy and endurance not materially affected because this is in‑memory compression. Evidence documents autotuning and kernel constraints [2].  \n10. Applicability across tiers: most beneficial on mid/large GPUs where VRAM is scarce; on 4 GB laptops benefit is limited unless GPU‑side decode is available or CPU decompression is efficient (evidence shows CPU decompressors exist but performance gaps are reported) [1][2][3].\n\n### 2) SSD/NVMe → GPU streaming with GPUDirect Storage (runtime streaming) (exact for MoE; limited for dense)\n1. Closest prior art: FlexGen and ZeRO‑Inference show disk/DRAM/GPU aggregation and streaming of weights; gdsllm demonstrates NVMe→VRAM streaming via GPUDirect Storage bypassing CPU RAM; NV developer documentation describes GPUDirect requirements [4][5][6].  \n2. Exact novelty claim: integrating GPUDirect streaming with layer‑granular, on‑GPU decompression + tiled matmul kernels for arbitrary quantized dense checkpoints is only partially realized — evidence shows MoE/experts benefit from streaming because many experts inactive, but dense models require full weight access and are not solved end‑to‑end [4][5][6].  \n3. Exactness conditions: SSD streaming can be exact if weights are streamed losslessly; evidence claims MoE streaming preserves output identicality in practice when only expert subsets are fetched, but for dense models throughput/latency tradeoffs remain [5].  \n4. Required changes: runtime‑only possible using GPUDirect and streaming libraries for GPUs that support them; no model retraining required for streaming, though MoE models are especially compatible [4][5][6].  \n5. Hardware/OS/driver assumptions: NVMe SSD with sequential read ~5,000–7,000 MB/s (PCIe4 examples), GPUDirect Storage support and required kernel/driver stack per NV docs [5][6].  \n6. Bandwidth/latency upper bound estimate: with NVMe sequential reads ~5–7 GB/s, a 16 GB weight set streamed sequentially takes ~2.3–3.2 s; GPUDirect direct transfer ceilings reported 40+ GB/s indicate much higher potential in optimized systems — precise throughput gains depend on working set locality and prefetching [5][6].  \n7. One‑week falsifying experiment: run gdsllm streaming on a single GPU with a MoE checkpoint (or a dense small checkpoint) and measure token latency and output identity vs fully‑loaded run; gdsllm repo provides code for NVMe→VRAM streaming [5]. Expected wall time: hours to set up; hardware: NVMe SSD and GPUDirect‑capable GPU per NV docs [6].  \n8. Likelihood of true novelty: medium — streaming exists but generalizing to dense arbitrary quantized checkpoints with fused decode kernels is underexplored [4][5][6].  \n9. Practical tradeoffs: increased latency, dependence on SSD endurance for hot weights, and implementation complexity; evidence comments on throughput/latency tradeoffs and SSD suitability [5].  \n10. Applicability across tiers: strong for MoE at low RAM because inactive experts reduce I/O; for dense models better for midrange systems with fast NVMe or GPUDirect; limited on 4 GB laptops without GPUDirect support [4][5][6].\n\n### 3) MoE speculative expert loading and hit‑rate guided prefetch (lossy→near‑exact via caching; exact when experts are deterministically preselected)\n1. Closest prior art: speculative expert loading (Mixtral example) fetches 1–4 likely experts with LRU replacement; fMoE and other works improve hit rate and reduce expert loading latency [10][11].  \n2. Exact novelty claim: evidence shows speculative expert loading exists; the gap is predictive prefetch policies tightly integrated with single‑checkpoint runtime that can guarantee exact outputs only when prefetch includes the true expert set deterministically (otherwise it is runtime‑equivalent but may increase misses) [10][11].  \n3. Exactness conditions: exact outputs are possible only if the runtime fetch set equals the experts chosen by the routing function; otherwise method remains exact if fallback fetch occurs before use (adds latency) — evidence reports staged speculative fetch with replacement policies [10][11].  \n4. Required changes: primarily runtime-only for serving existing MoE checkpoints; model changes are not required but model routing characteristics affect feasibility [10][11].  \n5. Hardware/OS/driver assumptions: fast storage/DRAM caching and ability to load expert weights quickly (evidence gives k=1–4 fetch sizes and mentions cache replacement) [10].  \n6. Bandwidth/latency upper bound: evidence shows that expert loading can dominate >80% of latency if mismanaged; speculative policies that reduce misses yield reported reductions but exact arithmetic depends on model expert sparsity stats in workload [10][11].  \n7. One‑week falsifying experiment: on a Mixtral‑like checkpoint, measure token latency and expert miss rate with and without speculative prefetch (sources provide methodology); time required: a few hours to run on hardware sized to fit a small expert cache [10][11].  \n8. Likelihood of true novelty: medium — improvements in prefetch heuristics remain active research but several systems already implement variants [10][11].  \n9. Practical tradeoffs: correctness depends on routing determinism; storage wear from repeated expert loads for hot experts; implementation complexity moderate [10][11].  \n10. Applicability across tiers: most valuable where expert library size exceeds RAM (edge→large server); on 4 GB machines MoE with high sparsity benefits most [10][11].\n\n### 4) KV‑cache management / paging / context streaming (system scheduling; mostly exact)\n1. Closest prior art: LLMS describes chunk‑based KV compression and optimized swapping for mobile; vLLM and related work use OS‑inspired paging and runtime pinning to manage KV cache and weights [12][13].  \n2. Exact novelty claim: integrated KV compression + global swapping policies tuned to token‑level access patterns for local devices remains underexplored; several works cover parts (chunk compression, hierarchical offload) but not a unified policy for constrained devices [12][13].  \n3. Exactness conditions: these approaches preserve outputs when KV cache values are recomputed or swapped losslessly; cited works claim near‑zero space waste and mobile‑focused implementations [12][13].  \n4. Required changes: runtime‑only in most cases; no training changes if compression/swapping is lossless [12][13].  \n5. Hardware/OS/driver assumptions: ability to page/stream memory and fast I/O; vLLM pinning and OS‑inspired approaches rely on standard host OS facilities [13].  \n6. Bandwidth/latency upper bound: empirical reports show large KV traffic driving DRAM saturation; concrete arithmetic depends on context length and model but sources provide empirical evidence of memory‑bound decode phases [12][13].  \n7. One‑week falsifying experiment: use vLLM pinning on a midrange GPU and measure per‑token latency as context grows, comparing swapped vs fully‑resident runs using a provided model (vLLM supports popular open models) [12][13].  \n8. Likelihood of true novelty: medium — many implemented components exist, but mobile‑focused end‑to‑end solutions are fewer [12].  \n9. Practical tradeoffs: recomputation vs storage tradeoff, increased latency on misses, developer complexity [12][13].  \n10. Applicability across tiers: helps all tiers where KV cache grows with context; greatest impact on constrained RAM/DRAM devices [12][13].\n\n### 5) Limits of speculative decoding for exact outputs (negative/structural result)\n1. Closest prior art: formal analysis shows exact‑matching acceptance probability for speculative decoding α_EM = Σ p(t)^2 is strictly <1 for non‑degenerate distributions; standard speculative decoding acceptance rate is Σ min{p(t),q(t)} and equals 1 only if draft equals target [8]. NAACL industry overview documents practical gains but also increased memory footprint for speculative approaches [9].  \n2. Exact novelty claim: the negative result is that speculative decoding cannot guarantee bit‑identical outputs unless the draft model is the identical target model (i.e., running the same model), which eliminates practical advantage for exactness unless the draft is an identical instance — this is demonstrated in the cited analysis [8][9].  \n3. Exactness conditions: exact bit‑identical outputs via speculative decoding require draft==target; otherwise probabilistic verification guarantees sampling‑distribution fidelity but not token‑wise identity [8].  \n4. Required changes: none — this is a theoretical limit; evidence does not show a workaround that preserves exact token identity without identical drafts [8][9].  \n5. Hardware/OS/driver assumptions: not applicable.  \n6. Bandwidth/latency upper‑bound estimate: acceptance rates limit speedups; the paper provides acceptance rate formulae that show speedups bounded by α_SD — numerical bounds depend on p and q which are model distributions [8].  \n7. One‑week falsifying experiment: compare greedy outputs using a target model vs outputs using speculative decoding with a different draft; measure acceptance rate and token mismatches — existing speculative decoding implementations and evaluation methodology are documented in industry sources [9][8].  \n8. Likelihood of true novelty: high for the negative claim (formal property proven) [8].  \n9. Practical tradeoffs: speculative decoding remains useful for latency but cannot deliver bit‑identical guarantees unless impractical duplication occurs [8][9].  \n10. Applicability across tiers: applies universally — speculative decoding is beneficial for throughput/latency but exactness cannot be preserved except in degenerate cases [8][9].\n\n### 6) CXL‑NDP and direct‑access remote memory offload (mixed exact potential)\n1. Closest prior art: CXL‑NDP introduces bit‑plane layouts and device‑side lossless compression with logical views for different quant formats; Direct‑Access‑Enabled GPU Memory Offloading (DAK) allows SMs to fetch offloaded data directly into shared memory bypassing HBM [14][15].  \n2. Exact novelty claim: combining CXL device‑side lossless bit‑plane storage with GPU direct fetch hardware to serve exact decompressed tiles on demand is promising and underexplored in a local inference context.  \n3. Exactness conditions: device‑side lossless compression preserves exact values per the CXL‑NDP design; DAK enables fine‑grained fetches that can retain exactness if decompression is lossless [14][15].  \n4. Required changes: hardware feature availability; runtime can be adapted but full benefits require CXL‑NDP and direct‑access support that may not exist on consumer devices — evidence specifies device features but not consumer availability [14][15].  \n5. Hardware/OS/driver assumptions: CXL‑NDP support, CXL‑enabled memory modules, direct GPU remote memory engines (DAK) — evidence documents these technologies [14][15].  \n6. Bandwidth/latency upper bound: CXL-NDP claims bit‑plane reductions; DAK claims elimination of HBM staging — precise arithmetic depends on device bandwidth numbers not fully specified for consumer tiers in the evidence [14][15].  \n7. One‑week falsifying experiment: not fully executable on commodity consumer hardware per evidence; additional hardware is required — evidence does not specify how to emulate CXL‑NDP on common laptops [14][15].  \n8. Likelihood of true novelty: medium — conceptually sound but depends on emerging hardware [14][15].  \n9. Practical tradeoffs: hardware availability, integration complexity, and potential large gains if hardware is present [14][15].  \n10. Applicability across tiers: most applicable to datacenter and advanced servers; limited on 4 GB laptops unless CXL/DAK‑like features reach edge hardware [14][15].\n\n---\n\n## Negative results and theoretical limits (synthesis)\n- Speculative decoding cannot guarantee bit‑identical outputs unless the draft equals the target model; acceptance‑rate formulas show strict limits on exact acceptance [8].  \n- Streaming/SSD approaches can be exact only if weights are transferred losslessly and within acceptable latency budgets; MoE designs help because sparse activation reduces I/O, while dense models remain memory/I/O bound despite streaming (documented in FlexGen/ZeRO and streaming reports) [4][5][6].  \n- Lossless compression approaches approach information‑theoretic limits for BF16/FP formats per DFloat11/ZipNN evidence; substantial further lossless gains are therefore limited unless novel coding assumptions or model‑format changes are introduced [1][3].\n\n## Evidence gaps\n- No primary sources in the provided findings demonstrate a portable, consumer‑grade runtime that fuses lossless decompression with general CUDA‑independent kernels for 4 GB laptop GPUs. Evidence either targets server/Hopper kernels or specific GPU requirements [1][2][6].  \n- Quantitative SSD endurance/energy arithmetic for high‑rate streaming on edge devices is not provided in the findings; further measurement access to SSD endurance profiles under streaming workloads would be required.\n\n## Shortlist (ranked)\nPursue\n- Lossless in‑compute compression + fused decompression runtime (Gap 1) — medium‑high novelty, broad applicability [1][2][3].  \n- SSD/NVMe → GPU streaming integrated with fused decompression for MoE/dense hybrids (Gap 2) — practical, immediate wins for MoE [4][5][6].\n\nInvestigate\n- MoE speculative expert loading with tighter prefetch policies (Gap 3) — useful for MoE; feasibility depends on routing determinism [10][11].  \n- KV‑cache chunking and global swapping tuned for edge devices (Gap 4) — strong cross‑tier impact but many components exist [12][13].  \n- CXL‑NDP + direct GPU fetch when hardware available (Gap 6) — high upside but hardware‑dependent [14][15].\n\nReject (for exact bit‑identical output)\n- Expectation that speculative decoding can yield bit‑identical outputs from a different draft model — formal analysis rules this out (Gap 5) [8][9].\n\n## References\n[1] https://arxiv.org/html/2504.11651v3  \n[2] https://research.cloudflare.com/papers/unweight-2026.pdf  \n[3] https://arxiv.org/html/2508.19263v1  \n[4] https://arxiv.org/html/2303.06865  \n[5] https://github.com/rscunha13/gdsllm  \n[6] https://mindstudio.ai/blog/ssd-streaming-ai-models-ram-dial  \n[7] https://docs.nvidia.com/gpudirect-storage/release-notes/index.html  \n[8] https://arxiv.org/html/2502.05202v3  \n[9] https://aclanthology.org/2024.naacl-industry.2.pdf  \n[10] https://arxiv.org/html/2603.19289v1  \n[11] https://chatpaper.com/paper/106437  \n[12] https://arxiv.org/html/2504.19720v1  \n[13] https://github.com/vllm-project/vllm/issues/3563  \n[14] https://arxiv.org/html/2509.03377v1  \n[15] https://arxiv.org/html/2604.26074v1  \n[16] https://developer.nvidia.com/blog/reducing-cold-start-latency-for-llm-inference-with-nvidia-runai-model-streamer",
